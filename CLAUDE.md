# LeafMD

A GNOME markdown viewer and editor in Rust (GTK4, libadwaita, GtkSourceView,
WebKitGTK), shipped as a Flatpak. README.md is for people using LeafMD (install,
features, shortcuts). docs/DEVELOPMENT.md has the table of what each source
file does, and docs/PUBLISHING.md covers releases and leafmd.app.

## How changes are planned: OpenSpec

`openspec/specs/` describes how LeafMD behaves today, one folder per area
(views, documents, recent-files, windows, links, formatted-view,
formatting-bar, find-replace, smart-typing, help-and-about, distribution,
desktop-integration). Read the relevant spec before
changing behaviour, and don't change behaviour a spec describes without
saying so.

- **Features and behaviour changes** (anything from ROADMAP.md, or anything a
  user would notice): start with `/opsx:propose`, get the owner's approval of
  the proposal, then `/opsx:apply`, then `/ship`, which archives the change
  once the owner has tried it. Archiving copies the change's new rules into
  `openspec/specs/`.
- **Small fixes** that don't change described behaviour (a crash, a typo, a
  tidy-up): no proposal needed. If a fix does change what a spec says, update
  that spec in the same commit.
- ROADMAP.md stays as the public "what's coming" list. Tick an item when its
  change is archived (`/ship` does this).
- Check specs with `openspec validate --specs --strict`. The `openspec` command
  needs Node 22 or newer (the nvm default).
- The files in `.claude/commands/opsx/` and `.claude/skills/openspec-*` are
  generated by OpenSpec. Don't edit them; `openspec update` rewrites them.

## How work gets released: `/ship`

```
/opsx:propose -> (owner approves) -> /opsx:apply -> /ship
```

`/ship` (`.claude/commands/ship.md`) owns everything after the code is
written: the checks, the owner's local test, commits, the version and release
notes, archiving, pushing, the pull request and resyncing after the merge. It
works out where things stand, so it's safe to run at any point. Use it rather
than doing those steps by hand; it is the authority on them.

Rules that hold even outside `/ship`:

- Work on **`dev`**. Never commit to `main`; it only changes through a pull
  request from `dev` that the owner merges on GitHub.
- Nothing is pushed until the owner has tried it in the installed Flatpak.
- Never merge a pull request, and never pick a version or decide to release
  without asking.
- The version is in `Cargo.toml` and the newest `<release>` in the metainfo
  file (same number, checked by `build-aux/release-info.py`). A `<release>`
  marked `type="development"` is unreleased; GitHub publishes a release when
  a merge into `main` carries one without that mark whose tag doesn't exist.
- A release also publishes leafmd.app (GitHub Pages): the storefront from
  `site/`, and the Flatpak repository installed copies update from, signed
  with LeafMD's key (the `LEAFMD_GPG_PRIVATE_KEY` secret; the public half is
  `build-aux/leafmd-signing-key.gpg`). Never print, copy or move that
  private key. `./build-aux/flatpak-repo-preview.sh` builds the same thing
  locally with a throwaway key, for trying before a release.
- Between releases, leafmd.app can be republished (`gh workflow run ci.yml
  --ref main -f republish=true`): `site/` from `main`, with the newest
  release's version, screenshots and repository, unchanged. Work that only
  touches the site or docs needs no new version. See docs/PUBLISHING.md.
- LeafMD isn't on Flathub, but it keeps to Flathub's rules:
  `build-aux/flathub-lint.sh` must pass. Don't add exceptions to
  `build-aux/flathub-lint-exceptions.json` without asking.

## Trying a change

The owner runs the installed Flatpak, not `cargo run`. After any change they
should try, run `./build-aux/flatpak-install.sh` (builds from the working
folder, about a minute), then ask them to close every LeafMD window and
reopen it. Don't close their running LeafMD yourself; it may have unsaved work.

Before that: `cargo build`, `cargo test` and `cargo clippy --all-targets -- -D
warnings` (no warnings at all; GitHub's build fails on any), and
`./build-aux/sdk-check.sh`, which runs the same checks GitHub does inside the
GNOME SDK.

## Every user-visible change also updates

- Help (`show_help` in src/window.rs) and Keyboard Shortcuts (`show_shortcuts`)
- README.md (features, shortcuts table) and, for new or renamed files, the
  file table in docs/DEVELOPMENT.md
- The app store description in `data/io.github.jeremehancock.LeafMD.metainfo.xml`
- The storefront at leafmd.app (`site/index.html`)
- The screenshots (`data/screenshots/`), if it changes how a window looks.
  `build-aux/take-screenshots.sh` takes them; `data/screenshots/README.md` has
  what to check afterwards
- The matching spec in `openspec/specs/`

## Conventions

- Code comments explain what and why in plain English, for someone who knows
  programming but not this codebase.
- Icons LeafMD draws itself live in one of two places. Icons with LeafMD's own
  names (`leafmd-...`) are in `data/resources/icons` and listed in
  `data/resources/resources.gresource.xml`. Icons with a standard name that
  replace Adwaita's, including ones GTK asks for itself like the window's
  buttons, are in `data/icon-theme/LeafMD`, because bundled icons can't replace
  Adwaita's. Draw them all with filled shapes only, because GTK doesn't paint
  outlined lines in symbolic icons.
- Nothing in a document may run scripts or navigate the formatted view away;
  see `openspec/specs/formatted-view` and `openspec/specs/links`.
- Commit to `dev`, only when the owner asks. Running `/ship` counts as asking.
